## 1. 测试概述

本轮对易淘商城 V1.0 进行了系统测试，覆盖用户、商品、购物车、订单四个模块的功能、
接口、数据一致性与安全性，并针对订单模块执行了并发测试与越权测试。

测试采用「手工 + 自动化」双轨：

- **自动化**：pytest 套件 105 条（含 13 条缺陷回归用例），可一键重跑，结果可复现。
- **手工**：浏览器走查 5 个页面 + Postman 直调接口 + Navicat 反向查库校验。

## 4. 质量评估

### 4.1 做得好

- 用户、商品、页面三个模块**全部用例通过**，主流程（浏览 → 加购 → 下单）走得通。
- 购物车的**跨用户隔离**实现正确：改/删他人购物车记录均返回 404，无越权。
- 订单列表 `/api/orders` 正确按 `user_id` 过滤。
- 库存流水机制设计合理，具备「用 SQL 反向校验数据一致性」的条件。
- 金额用 `DECIMAL` 存储，未出现浮点精度丢失。

### 4.2 做得不好

| 问题 | 影响面 | 关联缺陷 |
| --- | --- | --- |
| 状态机形同虚设（支付/取消不看当前状态） | 订单全流程 | BUG-001、BUG-002 |
| 关键写操作缺乏幂等保护 | 库存准确性 | BUG-002 |
| 库存扣减非原子，无并发控制 | 资金/库存损失 | BUG-003 |
| 资源归属校验缺失，接口层无鉴权 | 数据泄露、篡改 | BUG-004 |
| 入参校验不完整 | 脏数据 | BUG-005 |

**共性根因**：核心写路径（支付、取消、下单）**缺少「状态判断 + 原子操作 + 归属校验」**
这三道最基本的防线。4 个缺陷集中在订单模块，说明订单模块是质量短板。

## 5. 未通过项与风险

| 风险等级 | 风险描述 | 建议 |
| --- | --- | --- |
| 高 | 并发超卖（BUG-003）可能在秒杀/促销场景造成实际经济损失 | 上线前必修，用原子 UPDATE 或 `FOR UPDATE` |
| 高 | 订单越权（BUG-004）导致全量订单信息可被枚举泄露 | 上线前必修，接口层补鉴权 + SQL 限定 user_id |
| 中 | 状态机缺陷（BUG-001/002）导致账实不符、库存虚增 | 上线前必修，补状态前置校验 |
| 低 | 加购数量校验缺失（BUG-005）产生脏数据 | 可在下一迭代修复 |

**上线建议**：**不建议上线**。严重与高优先级缺陷共 4 个且全部未修复，
其中 2 个会造成直接的数据/资金损失，2 个属于安全类问题。
建议修复 BUG-001 ~ BUG-004 并回归通过后，再重新评估。

## 7. 后续计划

1. **开发修复**：BUG-001 ~ BUG-004 优先，修复方案见 `05-缺陷报告.md` 各条「修复建议」。
2. **回归验证**：
   ```bash
   pytest                       # 期望：全部 passed，无 xfailed
   pytest tests/bugs/ -v        # 修好后原 xfail 会变 XPASS 并报错
   ```
   修复后需把对应的 `xfail` 标记摘掉，改为正向断言。
3. **扩充测试**：
   - 用 Fiddler 抓包核对请求头 token 与参数完整性。
   - 用 Postman/Apifox 建立接口自动化集合，接入 CI。
   - 补充 SQL 注入、XSS 的基础安全用例。
4. **性能测试**：并发量提升至 50 / 100，观察响应时间与库存正确性。

---

## 8. 结论

易淘商城 V1.0 的**基础功能可用**：用户、商品、购物车、页面的常规流程全部通过，
代码结构清晰、分层合理（接口层 / 业务层 / 数据层）、提供了完整的需求与接口文档，
作为测试练习靶场达到了设计目标 —— 5 个典型缺陷（状态机、幂等、并发、越权、参数校验）
均可被测试手段稳定发现，且已用自动化用例固化。

但作为**生产系统**，V1.0 **不具备上线条件**：订单模块存在 2 个严重缺陷与 2 个高优先级缺陷，
涉及资损与数据安全，必须修复并回归通过后方可交付。
