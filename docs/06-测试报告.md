## 1. 测试概述

本轮对易淘商城 V1.0 进行了系统测试，覆盖用户、商品、购物车、订单、优惠券五个模块的
功能、接口、数据一致性与安全性，并针对订单模块执行了并发测试与越权测试。

测试采用「手工 + 自动化」双轨：

- **自动化**：pytest 套件 144 条（含 20 条缺陷回归用例），可一键重跑，结果可复现。
- **手工**：浏览器走查 6 个页面 + Postman 直调接口 + Navicat 反向查库校验。

> **关于 `xfailed`**：15 条未修复缺陷的回归用例用 `xfail(strict=True)` 标记。
> `XFAIL` = 「预期失败，且确实失败了」= **缺陷确认存在**。

### 3.4 缺陷修复与回归验证

本轮从 8 个缺陷中选取 2 个完成「**提交 → 定位 → 修复 → 回归验证 → 关单**」完整闭环，
其余 6 个维持待修复状态（作为后续迭代输入）。

| 缺陷 | 修改点 | 修复前 → 修复后 | 回归结论 |
| --- | --- | --- | --- |
| BUG-007 折扣券金额算反 | `service._calc_discount()` DISCOUNT 分支 | `discount = total × value` → `total × (1 − value)` | 199 元订单由「减 175.12 / 实付 23.88」修正为「减 23.88 / 实付 175.12」；2 条回归用例转正，手工用例 TC-COUPON-018 通过 |
| BUG-001 已取消订单可支付 | `service.pay_order()` 增加状态前置校验 | 无条件改状态 → 仅 `PENDING` 可支付，否则 400 `INVALID_STATUS` | 取消后支付由 200 变 400，订单状态不再被改写；2 条回归用例转正，手工用例 TC-ORDER-026 通过 |

**回归执行结果**：

```
修复前：124 passed, 20 xfailed
修复后：128 passed, 16 xfailed      ← 4 条 xfail 转正，0 失败
```

**修复带来的连锁影响（已一并处理）**：

1. `tests/bugs/test_bug_coupon_discount.py`、`test_bug_order_state.py` 中的
   4 条 `xfail(strict=True)` 用例在修复后触发 **XPASS**（套件变红），
   说明 `strict` 机制生效；已去除标记、改为正向断言，保留为长期防回归守卫。
2. `tests/test_order.py::TestPayOrder::test_pay_twice` 原先按旧行为断言
   「重复支付返回 200」，修复后该断言失效（用例变红）。
   **这条失败是有价值的信号**：它是靠套件自己暴露出来的，而不是靠人工排查。
   已改为断言 400 `INVALID_STATUS`。
3. 手工用例中因这两个缺陷而失败的结果改为通过（TC-ORDER-026、TC-COUPON-018 共 2 条），
   通过率 86.0% → **87.6%**（通过 104 → 106，失败 17 → 15）。
   注：TC-ORDER-027「取消已支付订单」同属状态机问题，但根因在 `cancel_order()`，
   本次不在修复范围内，仍保持失败状态。

> **为什么只修 2 个**：本项目定位是「测试靶场」——被测系统本身就是为练测试而写的。
> 修复的目的不是把系统改好，而是**验证测试链路能闭环**：
> 缺陷能被定位到代码行 → 修复建议可落地 → 回归用例能守住。
> 剩下 6 个缺陷继续留作练习与面试追问的素材。

## 4. 质量评估

### 4.1 做得好

- 用户、商品、页面三个模块**全部用例通过**，主流程（浏览 → 加购 → 下单）走得通。
- 购物车的**跨用户隔离**实现正确：改/删他人购物车记录均返回 404，无越权。
- 订单列表 `/api/orders` 正确按 `user_id` 过滤。
- 库存流水机制设计合理，具备「用 SQL 反向校验数据一致性」的条件。
- 金额用 `DECIMAL` 存储，未出现浮点精度丢失。
- 优惠券的**门槛校验、过期校验、归属校验**实现正确（用他人券返回 404，未达门槛拒绝）。
- 订单金额恒等式 `amount = total_amount − discount_amount` 在正确路径上成立。

### 4.2 做得不好

| 问题 | 影响面 | 关联缺陷 |
| --- | --- | --- |
| 状态机形同虚设（支付/取消不看当前状态） | 订单全流程 | BUG-001、BUG-002 |
| 关键写操作缺乏幂等保护 | 库存准确性 | BUG-002 |
| 库存扣减非原子，无并发控制 | 资金/库存损失 | BUG-003 |
| 资源归属校验缺失，接口层无鉴权 | 数据泄露、篡改 | BUG-004 |
| 入参校验不完整 | 脏数据 | BUG-005、BUG-008 |
| 「券值」语义一列两义，折扣率被当减免比例 | 资损（金额算错） | BUG-007 |
| 券状态机（未用→已用）在读券时未校验 | 资损（重复抵扣） | BUG-006 |

**共性根因**：核心写路径（支付、取消、下单、用券）**缺少「状态判断 + 原子操作 + 归属校验」**
这三道最基本的防线。8 个缺陷中订单模块 4 个、优惠券模块 3 个，说明「交易 + 促销」
这条链路是质量短板 —— 促销金额计算尤其容易被漏测。

## 5. 未通过项与风险

| 风险等级 | 风险描述 | 建议 |
| --- | --- | --- |
| 高 | 并发超卖（BUG-003）可能在秒杀/促销场景造成实际经济损失 | 上线前必修，用原子 UPDATE 或 `FOR UPDATE` |
| 高 | 订单越权（BUG-004）导致全量订单信息可被枚举泄露 | 上线前必修，接口层补鉴权 + SQL 限定 user_id |
| 高 | 折扣券金额算反（BUG-007）直接造成资损，且金额恒等式仍然「平」，极难被发现 | 上线前必修，用 `total×(1-value)` 重算并补单测 |
| 中 | 已用券可重复抵扣（BUG-006）造成重复优惠 | 上线前必修，读券时校验 `status == UNUSED` |
| 中 | 状态机缺陷（BUG-001/002）导致账实不符、库存虚增 | 上线前必修，补状态前置校验 |
| 低 | 加购数量校验缺失（BUG-005）、领券限领缺失（BUG-008）产生脏数据 | 可在下一迭代修复 |

**上线建议**：**不建议上线**。严重与高优先级缺陷共 6 个且全部未修复，
其中 4 个会造成直接的数据 / 资金损失（超卖、折扣算反、重复抵扣、库存虚增），
2 个属于安全类问题（越权）。建议修复 BUG-001 ~ BUG-007 并回归通过后，再重新评估。

## 8. 结论

易淘商城 V1.0 的**基础功能可用**：用户、商品、购物车、页面的常规流程全部通过，
代码结构清晰、分层合理（接口层 / 业务层 / 数据层）、提供了完整的需求与接口文档，
作为测试练习靶场达到了设计目标 —— 8 个典型缺陷（状态机、幂等、并发、越权、参数校验、
券状态、金额计算、限领校验）均可被测试手段稳定发现，且已用自动化用例固化。

但作为**生产系统**，V1.0 **不具备上线条件**：订单与优惠券模块存在 3 个严重缺陷与
3 个高优先级缺陷，涉及资损与数据安全，必须修复并回归通过后方可交付。
