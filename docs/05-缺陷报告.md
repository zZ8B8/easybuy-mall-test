## BUG-001 · 已取消的订单仍可被支付（状态机被击穿）

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-001 |
| 标题 | `POST /api/orders/{id}/pay` 不校验订单当前状态，CANCELLED 订单可被支付成功 |
| 模块 | 订单模块 |
| 严重度 | 高 |
| 优先级 | P0 |
| 状态 | 待修复 |
| 关联需求 | REQ-ORDER-008（仅待支付订单可支付） |
| 关联用例 | TC-ORDER-026、TC-ORDER-027 |
| 发现方式 | 接口测试 + 状态机测试 |
| 复现概率 | 100% |

### 环境
MariaDB 10.4.14 · Flask 3.1 · `http://127.0.0.1:5001` · 账号 `demo`/`123456`

### 前置条件
1. 数据库已初始化，`demo` 登录并拿到 token。
2. 购物车中有一件商品（如 P4 纯棉短袖 T 恤 ×1）。

### 复现步骤
1. 下单生成一笔订单：`POST /api/orders`，body `{"cartIds":[1]}` → 得到 `orderId`，状态 `PENDING`。
2. 取消该订单：`POST /api/orders/{orderId}/cancel` → 状态变为 `CANCELLED`，库存已回滚。
3. **对已取消的订单发起支付**：`POST /api/orders/{orderId}/pay`。

### 实际结果
- 第 3 步返回 **HTTP 200**，`{"code":"OK"}`。
- 订单状态从 `CANCELLED` **变回 `PAID`**，`paid_at` 被写入。
- 但库存**不会重新扣减** —— 出现「已支付但货没扣」的账实不符。

```json
// 第 3 步响应
{
  "code": "OK",
  "data": {
    "id": 1, "status": "PAID", "pay_type": "ALIPAY",
    "paid_at": "2026-10-05 15:42:10",
    "items": [{ "product_id": 4, "product_name": "纯棉短袖T恤",
                "price": 59.9, "quantity": 1 }]
  }
}
```

### 期望结果
- 支付接口应先检查订单状态：只有 `PENDING` 才允许支付。
- 对 `CANCELLED` / `PAID` 状态的订单，应返回 **400 `INVALID_STATUS`**（或等价错误码），
  并保持订单状态不变。

### 影响
- 状态机被击穿，业务上「取消 → 支付」这条非法路径被执行成功。
- 若对接真实支付，会直接造成**资金已收但库存未扣**，进而超卖。
- 状态字段失去可信度，下游报表、对账口径全部失真。

### 根因分析
`service.py` → `pay_order()`：直接执行 `UPDATE orders SET status='PAID' ...`，
**没有任何 `WHERE status='PENDING'` 条件，也没有前置 if 判断**。

```python
def pay_order(order_id, pay_type=None):
    order = db.fetch_one("SELECT id, status FROM orders WHERE id = %s", (order_id,))
    if not order:
        raise ApiError("ORDER_NOT_FOUND", "订单不存在", 404)
    # ⚠️ 这里读到了 order["status"] 却完全没用
    db.execute("UPDATE orders SET status=%s, pay_type=%s, paid_at=NOW() WHERE id=%s",
               (ORDER_PAID, pay_type or "ALIPAY", order_id))
```

### 修复建议
```python
if order["status"] != ORDER_PENDING:
    raise ApiError("INVALID_STATUS",
                   "订单当前状态为 %s，不可支付" % order["status"], 400)
```
并且把「判断 + 更新」放进同一事务，用带状态条件的 UPDATE 保证原子性：
`UPDATE orders SET status='PAID' ... WHERE id=%s AND status='PENDING'`，
再检查 `rowcount == 1`。

### 回归用例
`tests/bugs/test_bug_order_state.py::test_cancelled_order_should_not_be_paid`
`tests/bugs/test_bug_order_state.py::test_paid_order_should_not_be_paid_again`

## BUG-002 · 重复取消订单导致库存重复回滚（不幂等）

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-002 |
| 标题 | 同一订单可被重复取消，每次取消都回滚一次库存，商品凭空增多 |
| 模块 | 订单模块 |
| 严重度 | 高 |
| 优先级 | P0 |
| 状态 | 待修复 |
| 关联需求 | REQ-ORDER-009 / REQ-ORDER-010（取消幂等） |
| 关联用例 | TC-ORDER-028、TC-ORDER-029 |
| 发现方式 | 幂等性测试 + 数据一致性反向校验 |
| 复现概率 | 100% |

### 环境
同上。

### 前置条件
1. `demo` 已登录。
2. P4 纯棉短袖 T 恤初始库存 = 100，且无其他未完成订单占用。

### 复现步骤
1. 加购 P4 ×1，下单 → P4 库存变为 **99**。
2. 第一次取消订单：`POST /api/orders/1/cancel` → P4 库存回到 **100**（正确）。
3. **再次取消同一订单**：`POST /api/orders/1/cancel`。

### 实际结果
- 第 3 步返回 **HTTP 200**，`{"code":"OK"}`。
- P4 库存从 100 变成 **101**（若连续取消 3 次则为 102）。
- `stock_logs` 中该订单出现 **2 条** `ORDER_CANCEL` 记录（change_qty 均为 +1）。

```sql
-- 复现后查流水
SELECT * FROM stock_logs WHERE order_id = 1 AND reason = 'ORDER_CANCEL';
-- id | product_id | change_qty | reason        | order_id
-- 12 |     4      |     1      | ORDER_CANCEL  |    1
-- 13 |     4      |     1      | ORDER_CANCEL  |    1     ← 多出来的
```

### 期望结果
- 取消操作必须**幂等**：第一次取消成功后状态为 `CANCELLED`，
  再次取消应返回 **400 `INVALID_STATUS`**，且**不再回滚库存、不再写流水**。

### 影响
- **库存凭空增加**，商品数量与实际不符，直接造成超卖（前端显示有货、实际无货）。
- 库存流水被污染，`stock == SUM(change_qty)` 虽然仍自洽（因为两侧都加了），
  但**与真实进销存不符** —— 是典型的「数据看起来对、业务是错的」。
- 若接口被重复触发（用户连点、网络重试、爬虫），损失会被放大。

### 根因分析
`service.py` → `cancel_order()`：查询订单时**只取了 `id`，没有取 `status`，也没有状态判断**，
无条件把状态改为 `CANCELLED` 并回滚库存。

```python
def cancel_order(order_id):
    order = db.fetch_one("SELECT id FROM orders WHERE id = %s", (order_id,))
    if not order:
        raise ApiError("ORDER_NOT_FOUND", "订单不存在", 404)
    items = db.fetch_all("SELECT product_id, quantity FROM order_items WHERE order_id=%s", ...)
    # ⚠️ 没有判断当前状态，第二次进来又会把库存加一遍
    db.execute("UPDATE orders SET status='CANCELLED' WHERE id=%s", (order_id,))
    for it in items:
        db.execute("UPDATE products SET stock = stock + %s WHERE id=%s", ...)
        db.execute("INSERT INTO stock_logs ...")
```

### 修复建议
1. 先取 `status`，仅当 `PENDING` 时允许取消：
   ```python
   order = db.fetch_one("SELECT id, status FROM orders WHERE id = %s", (order_id,))
   if order["status"] != ORDER_PENDING:
       raise ApiError("INVALID_STATUS", "订单不可取消", 400)
   ```
2. 用「带条件更新 + 检查影响行数」保证并发下也只成功一次：
   ```sql
   UPDATE orders SET status='CANCELLED' WHERE id=%s AND status='PENDING';
   -- rowcount == 0 说明已被别人取消，直接返回错误，不再回滚库存
   ```
3. 库存回滚与流水写入放在**同一事务**内。

### 回归用例
`tests/bugs/test_bug_cancel_idempotent.py::test_double_cancel_should_not_twice_restore_stock`
`tests/bugs/test_bug_cancel_idempotent.py::test_double_cancel_should_not_duplicate_stock_log`

## BUG-003 · 并发下单超卖，库存被扣成负数

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-003 |
| 标题 | 「读库存」与「扣库存」非原子，并发下单导致超卖、库存为负 |
| 模块 | 订单模块 |
| 严重度 | **严重** |
| 优先级 | P0 |
| 状态 | 待修复 |
| 关联需求 | REQ-ORDER-012 / NFR-002 |
| 关联用例 | TC-ORDER-033、TC-CONC-001 |
| 发现方式 | 并发测试 |
| 复现概率 | 宽竞态窗口下 100%（窄窗口下偶现） |

### 环境
同上。测试时服务以多线程模式运行（`threaded=True`）。

### 前置条件
- P3 移动电源库存 = **3**。
- 准备 20 个并发请求。

### 复现步骤
1. 用 20 个线程，通过 `threading.Barrier` 对齐起跑时刻，同时发起：
   `POST /api/orders`，各自下单 P3 ×1。
2. 等全部返回后，查询 P3 库存与成功订单数：
   ```sql
   SELECT stock FROM products WHERE id = 3;
   SELECT COUNT(*) FROM orders WHERE status='PENDING';
   ```

### 实际结果
- P3 库存为 **-2**（或更负），**成功下单 5 笔** —— 卖出了 5 件，但只有 3 件库存。
- 库存流水 `SUM(change_qty)` 与 `stock` 仍然相等（两侧一起被扣），
  所以**只查流水看不出问题，必须看库存是否为负**。

```
期望：最多 3 笔成功，库存最终 = 0
实际：5 笔成功，库存 = -2
```

### 期望结果
- 无论多少并发，成功下单数 ≤ 库存数，库存不得为负。
- 同一时刻对同一商品的库存扣减必须互斥或原子。

### 影响
- **直接的经济损失**：超卖订单无法发货，需赔付或强制退款。
- 库存数据不可信，影响采购、补货、报表全部环节。
- 这是电商系统最典型、后果最严重的并发缺陷之一。

### 根因分析
`service.py` → `create_order()` 把库存操作拆成了**两步无保护的数据库交互**：

```
第一步：SELECT stock FROM products WHERE id=?      （普通查询，无锁）
        if stock < quantity: 拒绝
        ─────────── 竞态窗口（一次网络往返 + 线程调度）───────────
第二步：UPDATE products SET stock = stock - quantity WHERE id=?
```

多个线程在第一步都读到 `stock = 3 ≥ 1`，于是**都通过了校验**，
到第二步各自执行扣减，3 - 1 - 1 - 1 - 1 - 1 = -2。

```python
# ---- 第一步：逐个读商品、校验（普通非锁定查询）----
product = db.fetch_one("SELECT id, name, price, stock, status FROM products WHERE id=%s", ...)
if product["stock"] < c["quantity"]:
    raise ApiError("INSUFFICIENT_STOCK", ...)
checked.append((product, c["quantity"]))

# ---- 第二步：扣减库存（与第一步之间无事务/无锁）----
db.simulate_round_trip()   # 靶场显式化这段时间
db.execute("UPDATE products SET stock = stock - %s WHERE id=%s", ...)
```

> **关于 `simulate_round_trip()`**：真实系统中这两步之间必然隔着一次数据库往返和线程调度，
> 那就是竞态窗口。本机数据库同机访问太快，窗口小到偶现，因此靶场把这个延迟显式化
> （`config.SIMULATE_DB_LATENCY`，默认 0.05s，并发用例中放大到 0.3s），
> 让缺陷**稳定复现**，可写进回归。把该值改为 0 即可观察到窗口消失后的表现。

### 修复建议（任选其一或组合）
1. **原子条件更新**（最轻量）：
   ```sql
   UPDATE products SET stock = stock - %s WHERE id = %s AND stock >= %s;
   -- 检查 rowcount：为 0 说明库存不足，回滚整单
   ```
2. **悲观锁**：在事务中 `SELECT ... FOR UPDATE` 锁住商品行，再校验、扣减、提交。
3. **乐观锁**：给 products 加 `version` 字段，更新时带上版本号，失败则重试或报错。
4. **业务补偿**：整单放在一个事务里，任何一步失败全部回滚，并把「校验 + 扣减」合并为一步。

推荐 **方案 1 + 整单事务**：改动最小、无需引入重试逻辑、对当前架构友好。

### 回归用例
`tests/bugs/test_bug_stock_concurrency.py::test_concurrent_order_should_not_oversell`
（宽竞态窗口 fixture：`config.SIMULATE_DB_LATENCY = 0.3`，20 线程 Barrier 对齐）

## BUG-004 · 订单接口未校验归属，可越权操作他人订单（IDOR）

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-004 |
| 标题 | 查询 / 取消订单仅凭订单号即可操作，未校验订单所属用户 |
| 模块 | 订单模块 |
| 严重度 | **严重** |
| 优先级 | P0 |
| 状态 | 待修复 |
| 关联需求 | REQ-ORDER-013 / NFR-004 |
| 关联用例 | TC-ORDER-030、TC-ORDER-031、TC-ORDER-032 |
| 发现方式 | 越权测试（水平越权 / IDOR） |
| 复现概率 | 100% |

### 环境
同上。

### 前置条件
1. `user_a` 登录，下单生成订单 `order_id = 1`（**属于 user_a**）。
2. `user_b` 登录，拿到自己的 token。

### 复现步骤
1. **user_b 查询 user_a 的订单**：
   ```
   GET /api/orders/1
   Authorization: Bearer <user_b 的 token>
   ```
2. **user_b 取消 user_a 的订单**：
   ```
   POST /api/orders/1/cancel
   Authorization: Bearer <user_b 的 token>
   ```
3. **枚举订单号**：user_b 依次请求 `/api/orders/1`、`/2`、`/3`……

### 实际结果

**步骤 1** —— 返回 **HTTP 200**，user_b 拿到了 user_a 的完整订单信息：

```json
{
  "code": "OK",
  "data": {
    "id": 1, "user_id": 1, "amount": 199.0, "status": "PENDING",
    "created_at": "2026-10-05 15:50:00",
    "items": [{ "product_id": 1, "product_name": "无线蓝牙耳机",
                "price": 199.0, "quantity": 1 }]
  }
}
```

**步骤 2** —— 返回 **HTTP 200**，user_a 的订单**被 user_b 取消**，库存被回滚。

**步骤 3** —— 遍历 1~5 号订单，全部返回 200，**订单明细全量泄露**。

### 期望结果
- 查询 / 支付 / 取消订单时，必须校验 `order.user_id == 当前登录用户.id`。
- 不匹配时应返回 **404 `ORDER_NOT_FOUND`**（推荐，避免暴露「订单存在」这一信息）
  或 403 `FORBIDDEN`。
- 注意：`GET /api/orders`（列表）已正确按 user_id 过滤，只有详情/支付/取消漏了。

### 影响
- **用户隐私与业务数据泄露**：订单号可枚举，攻击者能拿到全部用户的购买记录、
  金额、时间、商品明细。
- **可越权写入**：任意用户可取消他人订单，属于数据篡改。
- 典型的 **IDOR（Insecure Direct Object Reference，不安全的直接对象引用）**，
  是 OWASP Top 10 中的常见高危项。
- 若还有其他依赖订单号的接口（退款、发货），同类问题会成片出现。

### 根因分析
`service.py` → `get_order()` / `cancel_order()`：

```python
def get_order(order_id):
    # ⚠️ WHERE 只用了 id，没有 user_id
    order = db.fetch_one("SELECT ... FROM orders WHERE id = %s", (order_id,))
    if not order:
        raise ApiError("ORDER_NOT_FOUND", "订单不存在", 404)
    ...

def cancel_order(order_id):
    # ⚠️ 同上，且 app.py 里这两个路由连鉴权都没加
    order = db.fetch_one("SELECT id FROM orders WHERE id = %s", (order_id,))
```

同时 `app.py` 中三条路由**根本没有调用 `auth_user()`**：

```python
@app.route("/api/orders/<int:order_id>")            # 无鉴权
@app.route("/api/orders/<int:order_id>/pay", ...)   # 无鉴权
@app.route("/api/orders/<int:order_id>/cancel", ...)# 无鉴权
```

**两层都漏了**：接口层没鉴权、服务层没校验归属。

### 修复建议
1. 接口层补上身份：三个路由都调用 `user = auth_user()`，并把 `user["id"]` 传入 service。
2. 服务层在 SQL 中直接限定归属（最稳，避免忘记判断）：
   ```sql
   SELECT ... FROM orders WHERE id = %s AND user_id = %s
   ```
   查不到统一按 `ORDER_NOT_FOUND` 返回，不区分「不存在」与「不属于你」。
3. 支付、取消、退款等所有按 ID 操作的接口，逐一排查同类问题。

### 回归用例
`tests/bugs/test_bug_authz.py::test_user_should_not_view_others_order`
`tests/bugs/test_bug_authz.py::test_user_should_not_cancel_others_order`
`tests/bugs/test_bug_authz.py::test_user_should_not_enumerate_others_orders`

## BUG-005 · 加购不校验数量，0/负数/超库存均可加入

| 项 | 内容 |
| --- | --- |
| 缺陷编号 | BUG-005 |
| 标题 | `POST /api/cart/items` 不校验 quantity 的取值范围，非法数量被接受 |
| 模块 | 购物车模块 |
| 严重度 | 中 |
| 优先级 | P1 |
| 状态 | 待修复 |
| 关联需求 | REQ-CART-001 |
| 关联用例 | TC-CART-006、TC-CART-007、TC-CART-008 |
| 发现方式 | 参数边界测试 |
| 复现概率 | 100% |

### 环境
同上。

### 前置条件
- `demo` 已登录。
- P3 移动电源库存 = 3；P4 纯棉短袖 T 恤库存 = 100。

### 复现步骤
分别发起三次加购请求：
1. `POST /api/cart/items`，body `{"productId":4,"quantity":0}`
2. `POST /api/cart/items`，body `{"productId":4,"quantity":-3}`
3. `POST /api/cart/items`，body `{"productId":3,"quantity":999}`

### 实际结果
三次请求**全部返回 HTTP 200**，非法数量被原样写入购物车：

```json
// 步骤 1
{ "code": "OK", "data": { "cartId": 1, "quantity": 0 } }
// 步骤 2
{ "code": "OK", "data": { "cartId": 1, "quantity": -3 } }
// 步骤 3
{ "code": "OK", "data": { "cartId": 2, "quantity": 999 } }
```

- 数量为 `0`、`-3` 的购物车记录被正常创建，前端会显示「0 件」甚至「-3 件」。
- 数量 `999` 远超库存 `3`，也被接受（校验被推迟到了下单那一步）。

### 期望结果
| 输入 | 期望 |
| --- | --- |
| quantity = 0 | 400 `INVALID_PARAM`：数量必须大于 0 |
| quantity < 0 | 400 `INVALID_PARAM`：数量必须大于 0 |
| quantity > 库存（如 999 > 3） | 400 `INSUFFICIENT_STOCK`，提示剩余库存 |
| quantity > 99（单笔上限） | 400 `INVALID_PARAM`：单笔最多 99 件 |

### 影响
- 购物车数据出现无意义的 0 / 负数记录，页面显示异常。
- 非法数据流到下单环节才被拦截，用户体验差（结算时才发现买不了）。
- 负数数量的记录若被下游逻辑直接使用（如金额计算、库存预占），
  可能引发**金额为负**等更严重的问题。
- 属于典型的「缺少参数有效性校验」，是接口测试必查项。

### 根因分析
`service.py` → `add_to_cart()`：只校验了商品是否存在、是否在售，
**完全没有校验 quantity**。

```python
def add_to_cart(user_id, product_id, quantity):
    if quantity is None:
        raise ApiError("INVALID_PARAM", "缺少 quantity", 400)
    # ⚠️ 只判了「有没有传」，没判「传的值是否合法」
    product = db.fetch_one("SELECT id, status FROM products WHERE id = %s", (product_id,))
    ...
    db.execute("INSERT INTO carts ... ON DUPLICATE KEY UPDATE quantity = quantity + VALUES(quantity)", ...)
```

### 修复建议
在 `add_to_cart` 中补上范围校验（并注意**累加后**的总量也要校验）：

```python
if not isinstance(quantity, int) or quantity <= 0:
    raise ApiError("INVALID_PARAM", "数量必须为正整数", 400)
if quantity > MAX_ORDER_QUANTITY:
    raise ApiError("INVALID_PARAM", "单次最多添加 %d 件" % MAX_ORDER_QUANTITY, 400)
if product["stock"] < quantity:
    raise ApiError("INSUFFICIENT_STOCK", "库存不足，当前仅剩 %d 件" % product["stock"], 400)
```

> 另外，`update_cart_quantity()` 有同样的缺失，修复时应一并处理。
