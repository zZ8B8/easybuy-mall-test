**如何解读 5 条「期望失败」**：
这 5 条用例断言的是「正确系统应有的行为」（如「已取消订单不可支付」）。
当前被测系统确实不满足这些断言，所以它们失败 —— 失败即证明缺陷被真实抓到。
用 `xfail` 而非普通失败标记，好处是：**一旦缺陷被修复，用例会自动变成 `XPASS` 提醒回归**。

## 4. 缺陷汇总

| 编号 | 标题 | 级别 | 类型 | 状态 |
|---|---|---|---|---|
| BUG-001 | 已取消订单仍可支付成功 | 高 | 状态机 | 已复现 / 待修复 |
| BUG-002 | 重复取消订单导致库存虚增 | 高 | 幂等性 | 已复现 / 待修复 |
| BUG-003 | 并发下单超卖（库存扣成 −27） | 严重 | 并发 | 已复现 / 待修复 |
| BUG-004 | 可查看并取消他人订单 | 严重 | 越权 | 已复现 / 待修复 |

**缺陷分布**：订单/库存模块 3 个（BUG-001/002/003），权限模块 1 个（BUG-004）。
**共性根因**：缺少**状态前置校验**（001/002）与**请求归属校验**（004）；
003 属于典型的 check-then-act 竞态。三类问题都不是「代码写错了」，
而是「该校验的地方没校验」—— 这也说明用例设计时**优先攻击状态与边界**是有效的。

## 5. 测试结论

| 维度 | 评价 |
|---|---|
| 基本功能 | **通过**。主链路（注册 → 加购 → 下单 → 支付/取消）正常，参数校验完备 |
| 数据一致性 | **不通过**。取消接口非幂等，库存会被重复回滚（BUG-002）；并发下单超卖（BUG-003） |
| 状态正确性 | **不通过**。支付接口未校验订单状态，已取消订单可支付（BUG-001） |
| 权限控制 | **不通过**。订单接口未做归属校验，存在水平越权（BUG-004） |

**总体**：核心功能可用，但**不具备上线条件** —— 存在 2 个严重级缺陷（资损风险 + 安全风险）。
建议优先修复 BUG-003 与 BUG-004，并补充「状态前置校验」的统一收口。

## 6. 修复后的验证方式

修复代码后重新跑测试：

```bash
pytest tests/bugs -v
```

如果输出从 `xfail` 变成 **`xpass` / `passed`**，说明缺陷已被修复且没有引入回归。
`xfail` 用例在这里起到了**回归守护**的作用。

## 7. 遗留问题与建议

| # | 内容 | 建议 |
|---|---|---|
| 1 | 订单金额使用浮点运算（如 `99.99 × 3`）可能产生精度误差 | 生产系统应改用 `Decimal` 或「以分为单位的整数」计算 |
| 2 | 未做性能测试 | 补充并发上限、响应时间 P95 等指标 |
| 3 | 密码明文存储与传输 | 应加盐哈希（bcrypt）并强制 HTTPS |
| 4 | token 无过期机制 | 应引入有效期与刷新机制 |
| 5 | 商品下架后已在购物车中的条目如何处理 | 需明确业务规则并补用例 |
