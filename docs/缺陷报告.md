## BUG-001 · 已取消订单仍可支付成功

| 项 | 内容 |
|---|---|
| 级别 | **高** |
| 类型 | 状态机 / 业务逻辑 |
| 模块 | 订单 |
| 接口 | `POST /api/orders/{id}/pay` |
| 定位 | `sut/service.py` → `pay_order()` |

**复现步骤**

1. 注册登录，加购「无线蓝牙耳机」1 件，提交订单 → 订单状态 `PENDING`
2. 调用取消接口 → 订单状态 `CANCELLED`
3. 对同一订单调用支付接口，`payType=ALIPAY`

**预期结果**：支付失败，返回 400（订单状态非法，已取消的订单不可支付）

**实际结果**：返回 `HTTP 200`，订单状态由 `CANCELLED` 变为 `PAID`

```
取消后状态=CANCELLED
支付已取消订单 HTTP=200
支付后状态=PAID
```

**根因**：`pay_order()` 只校验了支付方式是否合法，**没有校验订单当前状态**：

```python
def pay_order(order_id, pay_type):
    order = get_order(order_id)
    if pay_type not in ("ALIPAY", "WECHAT", "CARD"):
        raise BizError("INVALID_PAY_TYPE", "不支持的支付方式")
    order["status"] = ORDER_PAID          # ← 无条件置为已支付
```

**影响**：用户可对已取消（库存已释放）的订单发起支付；若后续接入真实支付网关，
将出现「库存已回滚、钱却收了」的对账不平。

**修复建议**：支付前校验 `order["status"] == ORDER_PENDING`，否则抛
`BizError("ORDER_STATE_INVALID", "订单当前状态不可支付")`。

## BUG-002 · 重复取消订单导致库存虚增

| 项 | 内容 |
|---|---|
| 级别 | **高** |
| 类型 | 幂等性 / 数据一致性 |
| 模块 | 订单 / 库存 |
| 接口 | `POST /api/orders/{id}/cancel` |
| 定位 | `sut/service.py` → `cancel_order()` |

**复现步骤**

1. 加购「无线蓝牙耳机」2 件（初始库存 50），提交订单 → 库存 48
2. 第一次取消订单 → 库存回滚为 50（正确）
3. **再次**对同一订单调用取消接口
4. 读库存

**预期结果**：第二次取消被拒绝或幂等返回，库存保持 50

**实际结果**：返回 `HTTP 200`，库存被再次释放为 **52**（凭空多出 2 件）

```
初始库存=50
下单后=48
第一次取消 HTTP=200 -> 库存=50
第二次取消 HTTP=200 -> 库存=52（虚增 2 件）
```

**根因**：`cancel_order()` 只拦了「已支付订单不能取消」，**没有拦「已取消订单不能重复取消」**，
且回滚库存的循环无条件执行：

```python
def cancel_order(order_id):
    order = get_order(order_id)
    if order["status"] == ORDER_PAID:
        raise BizError("ORDER_PAID", "已支付订单不能取消")
    order["status"] = ORDER_CANCELLED
    for item in order["items"]:
        product["stock"] += item["quantity"]    # ← 重复执行就会重复加
```

**影响**：库存虚增 → 超卖 → 用户下单后无货可发。属于会直接造成资损的缺陷。

**修复建议**：
1. 取消前判断状态，非 `PENDING` 直接拒绝（幂等性守卫）；
2. 库存回滚改为写一条带唯一约束的流水，重复回滚会被数据库拒绝。

## BUG-003 · 并发下单超卖

| 项 | 内容 |
|---|---|
| 级别 | **严重** |
| 类型 | 并发 / 竞态条件（TOCTOU） |
| 模块 | 订单 / 库存 |
| 接口 | `POST /api/orders` |
| 定位 | `sut/service.py` → `create_order()` |

**复现步骤**

1. 选「移动电源 20000mAh」（初始库存 **3**）
2. 30 个用户各自加购 1 件（加购串行执行，排除干扰）
3. 30 个线程用 `threading.Barrier` 对齐后**同时**提交订单

**预期结果**：最多 3 笔下单成功，库存最终为 0，且不为负数

**实际结果**：**30 笔全部成功**，库存被扣成 **−27**

```
初始库存=3，并发用户=30
下单成功=30 笔，失败=0 笔
最终库存=-27
```

**根因**：`create_order()` 把「校验库存」和「扣减库存」写成前后两步，
中间没有锁保护，并发请求会在这段窗口内读到同一份旧库存：

```python
# 第一步：逐个校验库存
for cart in carts:
    if product["stock"] < cart["quantity"]:
        raise BizError("INSUFFICIENT_STOCK", ...)

# ← 窗口：并发请求在此读到同一份旧库存，于是全部通过校验
time.sleep(DB_ROUND_TRIP)          # 模拟两条 SQL 之间的持久层往返延迟

# 第二步：统一扣减
for item in order_items:
    product["stock"] -= item["quantity"]
```

**影响**：超卖，用户付款后无货；库存被扣成负数，会污染后续所有库存计算与补货决策。

**修复建议**（任一）：
1. **加锁**：对同一商品的校验 + 扣减加互斥锁（单机可用 `threading.Lock`，分布式用 Redis 锁）；
2. **原子扣减**：把「校验」改成条件更新 —— `UPDATE product SET stock = stock - n WHERE id = ? AND stock >= n`，
   依据影响行数判断是否成功（推荐，一行 SQL 解决）；
3. 队列串行化下单请求。

**备注**：`DB_ROUND_TRIP` 是对真实数据库往返延迟的显式模拟（真实系统中这段延迟来自
SQL 执行与网络 IO），用于把偶发的竞态缺陷变成稳定可复现。数值可调，不影响缺陷结论。

## BUG-004 · 可查看并取消他人订单（水平越权）

| 项 | 内容 |
|---|---|
| 级别 | **严重** |
| 类型 | 权限 / 安全 |
| 模块 | 订单 |
| 接口 | `GET /api/orders/{id}`、`POST /api/orders/{id}/cancel` |
| 定位 | `sut/server.py` → `api_order_detail()`、`api_order_cancel()` |

**复现步骤**

1. 用户 alice 下单，拿到订单号
2. 用户 bob 登录，用**自己的 token** 请求 `GET /api/orders/{alice的订单号}`
3. bob 再请求 `POST /api/orders/{alice的订单号}/cancel`
4. alice 查询自己的订单状态

**预期结果**：两步都返回 403（无权访问）或 404（对本人不可见）

**实际结果**：两步都返回 `HTTP 200`；alice 的订单被 bob **成功取消**

```
订单归属=alice，操作者=bob
bob 查 alice 订单 HTTP=200
bob 取消 alice 订单 HTTP=200
该订单最终状态=CANCELLED
```

**根因**：这两个接口只做了「认证」（`auth=True` 校验 token 是否有效），
**没做「授权」**（没校验订单是否属于当前用户）：

```python
@route("GET", "/api/orders/{id}", auth=True)
def api_order_detail(ctx):
    return service.get_order(ctx["params"]["id"])      # ← 没传 ctx["user"]
```

**影响**：任意登录用户只要猜/遍历订单号，就能读取他人订单明细（含商品、金额），
并恶意取消他人订单。属于线上严重安全事故级别。

**修复建议**：在 service 层统一收口，查询与操作订单时都带上 `user_id` 做归属校验，
不匹配时返回 404（而非 403，避免泄露「该订单存在」这一信息）。
